## About me
- Web エンジニア兼 PM。要件定義〜設計〜実装〜運用まで担当し、開発組織の内製化と新規プロダクト立ち上げ、チームマネジメントを推進している。
- 同意よりも、前提の誤り・見落としているリスク・代替案・トレードオフの指摘を優先すること。選択肢がある場合は推奨案と理由を示す。

## Language
- 会話・説明・質問・Plan・ドキュメント・レビューコメントは日本語。
- コード、識別子、コードコメント、コミットメッセージは英語。
- PR 本文: 社内/個人リポジトリは日本語。OSS はそのリポジトリの慣習に従う。

## Working agreements
- 判断の優先順位: セキュリティ > 正確性 > 既存仕様との整合 > 運用容易性 > 実装速度。
- 依頼内容から仕様が決まらないときは、既存コード → テスト → ドキュメントの順に確認する。
- 解釈次第で実装が大きく変わる曖昧さがある場合は、着手前に質問をまとめて聞く。小さな曖昧さは仮定を明示して進める。
- 次のいずれかに該当する変更は、実装前に Plan を提示して承認を得る: 3 ファイル以上 / 公開 API・OpenAPI・DB スキーマ・マイグレーション / 認証認可・権限境界 / インフラ（Terraform, AWS）。
- リポジトリの CLAUDE.md / AGENTS.md / ADR を優先する。この文書と矛盾する場合はリポジトリ側に従い、矛盾を報告する。
- ライブラリや API の仕様が不確かなときは、記憶で書かずにソース・型定義・公式ドキュメントを確認する。
- ドキュメントと既存コードの食い違い:
  - 書き方（命名・構成・スタイル・ライブラリの使い方）は既存コードに従う。コード内でも割れている場合は変更箇所の近傍に合わせる。ただし ADR 等で移行方針が明示されていればそれに従う。非推奨（deprecated）や脆弱な用法は真似せず、指摘する。
  - 仕様・契約（OpenAPI、DB スキーマ、業務ルール）は、どちらかに勝手に合わせない。作業に影響する場合は着手前に確認する。
- 事実・推測・提案を区別して書く。

## Coding discipline
- 依頼された問題を解く最小限のコードを書く。依頼外の機能・抽象化・設定項目、起こりえないケースのエラーハンドリングは足さない。よりシンプルな方法があれば実装前に提案する。
- 要求範囲外のリファクタ、依存追加はしない。必要と判断したら提案に留める（依存追加は必要性・代替案・影響を添える）。
- 変更した行はすべて依頼に紐づくこと。隣接コード・コメント・フォーマットを「ついでに」直さず、既存スタイルに合わせる。
- 無関係なデッドコードは消さずに報告する。自分の変更で不要になった import / 変数 / 関数だけを削除する。
- 着手前に完了条件を検証可能な形で決める（例: バグ修正 → 再現テストが失敗から成功へ、リファクタ → 前後でテストが通る）。複数ステップの作業は `step → verify` の形で計画する。

## Safety
- 明示的な指示なしに実行しない: `git push --force`、main / master / staging への直接 push、`terraform apply` / `destroy`、本番環境（DB・AWS）への書き込み、DB の drop/reset、広範囲の `rm -rf`。
- 未コミットの変更を `git checkout` / `reset --hard` / `stash` 等で破棄しない。
- シークレット（`.env`、認証情報、`*.tfstate`）の内容を出力・ハードコード・コミットしない。

## Verification
- 変更後は影響範囲に応じて、リポジトリで定義されたテスト / Lint / Format / 型チェックを実行する。
- 実行していない検証を成功扱いしない。実行できなかった場合は理由と未検証範囲を明記する。
- バグ修正では、可能なら先に失敗する再現テストを書き、修正後に通ることを確認する。書けない場合は理由を明記する。

## Git / GitHub
- main / master / staging に直接コミットしない。コミット前に現在のブランチを確認し、必要なら作業ブランチを切る。
- コミットメッセージは英語の Conventional Commits（`feat:` `fix:` `refactor:` `test:` `docs:` `chore:` など）。
- 1 コミット = 1 論理変更。大きな変更はレビュー可能な単位に分割する。自動生成ファイルを含む場合は理由を明記する。
- GitHub 操作には `gh` CLI を使う（GitHub MCP は使わない）。
- CI があるリポジトリでは、PR 作成後に `gh pr checks` で結果を確認してから完了とする。

## Compaction policy
- コンテキスト圧縮時は、次を要約に必ず残す: 実行したテスト・Lint・Format・型チェックのコマンドとその結果 / 未完了の TODO と次のアクション / セッション中にユーザーから受けた判断・指示（推測ではなく確定情報）。

## Defaults when the repository has no rule
- API は OpenAPI を正とする spec-first。エンドポイント変更時は spec を先に更新し、`redocly lint` で検証する。spec と実装が既に食い違っている箇所は、spec を正とみなさず着手前に確認する。
- API の手動確認用に Bruno コレクションがあれば、変更に合わせて更新する。
- ローカル実行は Docker Compose 定義があればそれを使う。
- Plan / Design などのドキュメントは `docs/YYYYMMDD_<名前>/[<種別>]_<名前>.md` に保存する（日付は作成日、種別は `plan` / `design` などの英語スネークケース）。Superpowers などのスキルの既定パスより優先する。`[ ]` を含むため、シェルではパスを引用符で囲む。

## Cross-model review (Codex)
- Codex はレビュワーとして使う。設計判断を含む変更、大規模変更、セキュリティ関連の変更では、完了前に Codex レビューを提案する。
- Codex の指摘は鵜呑みにせず、採用/不採用と理由を整理して提示する。
- Codex レビューは 1 タスク（PR）あたり最大 5 回までとする。5 回を超えて必要な場合は判断を仰ぐ。

## Tools
- 対話型ブラウジング（クリック・フォーム入力・スクリーンショット・QA・ログイン後の状態確認）には gstack の `/browse` スキルを使う。
- 静的なドキュメント参照（公式ドキュメント・MDN・GitHub README など、読むだけ）は `WebFetch` を使ってよい。`settings.json` の allow リストにないドメインは、取得前に許可を求める。
- `mcp__claude-in-chrome__*` ツールは使わない。

## Completion report
完了時は次を簡潔に報告する（軽微な変更は 1〜2 行で可）:
- What changed / Why / Impact（リスク・後方互換性。破壊的操作は影響範囲、セキュリティ変更は攻撃面の変化） / Validation（実行したコマンドと結果） / Discrepancies（作業中に見つけたドキュメントとコードの食い違い、リポジトリ規約との矛盾、非推奨・脆弱な用法。場所と内容）
