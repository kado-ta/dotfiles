# プロジェクトの運営を補佐する

ゴールと期限のあるプロジェクトについて、今の位置からゴールまでの道筋を整理する。中心はタスクとリスクの洗い出しで、決めるのはユーザー。道具の詳細は [REFERENCE.md](REFERENCE.md)、出力の形は [TEMPLATES.md](TEMPLATES.md) にある。

チケット 1 枚や 1 日のタスクの分解、開発中のコード変更や設計のリスク、何を作るかの判断（`/office-hours`）、機能の要件（`brainstorming`）、実装の計画（`writing-plans`）を頼まれたときは、このスキルの手順を使わない。

<a name="order"></a>

## 確かめる順番

決まった手順ではない。依頼に合わせて軽重を変える。ただし 5 のリスクは省かない。

<a name="current-state"></a>

### 1. 現状をつかむ

- 渡されたリンクや資料は、先に読む。使える手段（`gh`、MCP、WebFetch）で読めなければ、要点の貼り付けを頼む。読めなかった中身を推測で埋めない。
- 次の項目のうち、分からず、答えで進め方が変わるものだけを、5 件までにして聞く。ほかは仮に置き、前提として示す。

| 項目 | 確かめること |
| --- | --- |
| 目的 | なぜ今やるのか。やらないと何が困るか |
| 完了の定義 | 何ができたら終わりか。誰が受け入れるか |
| 期限 | 動かせない期限か、目安か。その根拠 |
| 体制 | 誰が、どれだけの時間で関わるか。決める人は誰か |
| 関係者 | 承認する人、影響を受ける人、報告する先 |
| 制約 | 予算、技術、契約、法令 |
| 現在地 | 終わったこと、終わっていないこと |

- 出す前にも、この表の項目に答えられるかを確かめる。答えられない項目は、前提か確認事項として出力に書く。

<a name="approach"></a>

### 2. 進め方の型を決める

2 つの軸で決め、判定とその理由を示す。

- 規模: 軽量型（目安は 5 人まで、3 か月まで、関係者と直接話せる、失敗しても手戻りで済む）か、エンプラ型（複数のチームや部署、半年以上、承認の階層、契約・法令・顧客への影響、外部への依存）か。間なら軽いほうから始め、要るものだけ足す。
- 不確実性: 答えが分かっている／調べれば分かる／やってみないと分からない／すぐ止血が要る、のどれか（[不確実性の分類](REFERENCE.md#uncertainty)）。やってみないと分からない案件では、細かい分解より、仮説と小さな検証をマイルストーンにする。

軽量型では、タスク・リスクの上位・次のアクションに絞り、WBS やステークホルダー登録簿のような重い成果物を作らない。エンプラ型では、関係者の分析、承認にかかる日数、コミュニケーション計画まで含める。

<a name="phase"></a>

### 3. フェーズを見極める

| フェーズ | 焦点 |
| --- | --- |
| 立ち上げ | 目的・ゴール・範囲の合意、関係者の特定、成功の基準 |
| 計画 | 分解、見積もり、依存、マイルストーン、リスクへの備え |
| 実行と監視 | 計画とのずれ、詰まり、新しいリスク、範囲の膨張 |
| 立て直し | 現実に合わせた計画の引き直し、削る候補、クリティカルパスの見直し |
| 終結 | 残作業、引き継ぎ、振り返り |

「〜のフェーズと見ています」と示して、ユーザーとすり合わせる。

<a name="tasks"></a>

### 4. タスクを洗い出す

- ゴールから逆算し、成果物（何ができあがるか）から分解する。直近は完了を判定できる粒度まで分け、遠い先は粗いままにする。
- 各タスクに担当（未定でよい）・依存・優先度を付け、マイルストーンとクリティカルパスを置く。
- 抜けやすいタスクを確かめる: 承認とレビューの待ち、環境の準備、テストと受け入れ、文書、周知、引き継ぎ、リリース後の監視。
- 見積もりで、根拠のない一点の数字を出さない。似た案件の実績を先に聞き、不確かなら幅で示す（[見積もり](REFERENCE.md#estimation)）。
- 抜けを探すときは、[抜けを見つける問い](REFERENCE.md#coverage)を使う。

<a name="risks"></a>

### 5. リスクを洗い出す（省かない）

タスクの整理だけを頼まれても、この節を出す。量は案件に合わせ、軽い依頼では上位 3 件と次のアクションにする。

- 5 つに分ける: リスク（まだ起きていない悪いこと）、前提（「〜のはず」で進めていること）、課題（もう起きていること）、依存（ほかのチームや外部の成果物・判断の待ち）、分かっていないこと（調べる・聞くタスクにする）。
- 毎回見る観点: 人（特定の人への依存、稼働の取り合い）、外部（他チーム・ベンダー・外部のシステム）、技術（試していない技術、性能、既存のシステムとの統合）、範囲（曖昧な要件、関係者の認識のずれ）、意思決定（決まらないと進めないこと）。
- 確率と影響で上位を決め、上位には対応の型・次のアクション・担当を付ける（[リスク](REFERENCE.md#risk)）。並べるだけで終わらない。
- 出尽くさないときと、キックオフやリリース前の節目では、[プレモーテム](REFERENCE.md#premortem)を使う。

<a name="output"></a>

### 6. まとめて出す

[TEMPLATES.md](TEMPLATES.md) の形で出す。次を必ず入れる。

1. 現状のまとめ（フェーズと型、その理由）
2. タスク
3. リスク（5 つの分類）
4. 次のアクション（今週から 2 週間で。3〜7 個）
5. 共有（誰に・何を・いつ伝えるか。先回りで伝えること）
6. 判断事項（元に戻せるか、決める人 1 人、期限、推奨と理由）。判断どうしに依存があれば親から並べ、親が決まっていない子は項目だけを挙げる。子の選択肢は親の答えで変わるため。

<a name="follow-up"></a>

## 2 回目以降

前回の結果から、終わったこと・遅れ・計画とのずれ・新しいリスクと消えたリスクを先に見る。前回の結果が手元になければ、貼り付けを頼む。

<a name="saving"></a>

## 保存

既定はチャットに出すだけにする。保存を頼まれたら、そのリポジトリの文書の規則に従う。規則がなければ、グローバルの文書の規則（DOCUMENTS.md）の作業文書として、作業ディレクトリの `plan.md` に置き（`status: in-progress`）、見直しは日付つきの節として足す。

<a name="principles"></a>

## 原則

- リスクの節のない出力で終わらない。
- 目的を問う。言われた作業をそのままタスクにせず、目的に照らして要らないものは「やらない」と提案する。
- プロセスや成果物を押し付けない。PMBOK などは道具箱で、案件に合わないものは使わない。
- 先回りで伝える。後から「あれはどうなった？」と聞かれない状態を、共有の計画に含める。
